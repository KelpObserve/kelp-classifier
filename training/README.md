# Training

Train and evaluate a binary kelp-presence classifier on top of frozen
[Clay v1.5](https://clay-foundation.github.io/model/) embeddings.

## Approach

1. **Fixed splits** — pre-computed train/val/test splits, one per seed (default
   seeds 42/123/456), generated by [`make_splits.py`](make_splits.py).
   The split algorithm ensures P and A share the same water, cloud, and (as
   closely as possible) b02\_range distributions within every split, so
   headline metrics reflect kelp signal rather than QC-metadata leakage.
2. **Precompute Clay embeddings** for every used chip once, cached to
   `$KELP_DATA_DIR/clay_cache/identity.npz`.
3. **Balanced training** — subsample the larger of (PRESENT, ABSENT) in train
   so both classes have equal count per batch.
4. **MLP head** on top of the 2048-D embedding (Clay CLS + centre-pool concat;
   pool size configurable via `KELP_POOL_SIZE`, default 5×5). Focal loss, α=0.5, γ=2.
5. **Model selection** by best val `macro\_f1`; test evaluated at threshold
   `0.5` (default) AND at `t*` (per-model threshold that maximises val
   `macro\_f1`).

## Clay model

- Checkpoint: `$KELP_DATA_DIR/clay/v1.5/clay-v1.5.ckpt` (4.9 GB)
- Band-stat metadata: `the repo /configs/metadata.yaml`
- Loaded via
  `claymodel.module.ClayMAEModule.load_from_checkpoint(..., model_size="large",
  shuffle=False, mask_ratio=0, map_location="cuda")`
  (map_location="cuda" avoids peak CPU-RAM pressure during the ckpt load).
- Encoder output: CLS token (1024-D) + mean of a central `POOL_SIZE × POOL_SIZE`
  window on the 28×28 patch grid → concatenated to 2048-D. Default pool 5×5
  (`patches[11:16, 11:16]`); see § "Centre-pool size" below to change it.

## Centre-pool size

The head's spatial embedding is the mean of a `POOL_SIZE × POOL_SIZE` window of
Clay patch tokens centred on the chip centre. `KELP_POOL_SIZE` (env var, read
in [`config.py`](../config.py)) controls it end-to-end: the aggregation done in
[`precompute_clay_embeddings.py`](precompute_clay_embeddings.py), the cache
filename (`clay_cache/identity_p{POOL_SIZE}.npz`), and the results directory
(`results/head_seed{SEED}_p{POOL_SIZE}/`) all pick it up from there.

**Why it exists.** GBIF/OBIS PRESENT records are point observations with
`coordinateUncertaintyInMeters ≤ 10 m` (after the current fetch tightening) —
one Sentinel-2 pixel of positional uncertainty. The chip is anchored on that
point (or its snapped water pixel for ABSENT). Smaller pool → the classifier's
decision is informed by a tighter neighbourhood around the anchor, at the cost
of spatial averaging that stabilised the historical 5×5 run. Larger pool →
more context, coarser effective footprint.

**How it flows through the pipeline.** The cache stores the raw CLS token +
the centre `CACHE_K × CACHE_K` (default 7×7) patch tokens per chip
([`patch_pool.py`](patch_pool.py)). Pool aggregation happens at head-training
time in [`train_head.py`](train_head.py) — it slices a `POOL_SIZE × POOL_SIZE`
window inside the cached 7×7, means it, and concatenates with CLS. One Clay
pass covers every pool size ≤ CACHE_K. To go above 7 (e.g. try pool=9), widen
`CACHE_K` and re-run precompute.

**Valid values and effective footprint.**

| `KELP_POOL_SIZE` | Patch slice on 28×28 grid | Effective footprint (native S2 metres) |
|---:|---|---|
| 1 | `[13:14, 13:14]`   | ~46 × 46 m   (1 Clay patch) |
| 2 | `[13:15, 13:15]`   | ~92 × 92 m   (2×2 patches straddling the true centre) |
| 3 | `[12:15, 12:15]`   | ~137 × 137 m |
| 5 | `[11:16, 11:16]`   | ~229 × 229 m (default; matches the historical run) |
| 7 | `[10:17, 10:17]`   | ~320 × 320 m |

The chip centre falls at patch ≈ 13.9 (chip pixel 111.5 in Clay's 224-space,
divided by the 8-pixel patch width). Odd pool sizes centre on patch 13 —
consistent with the original `[11:16]` window (11+15 midpoint = 13). Even pool
sizes take `[13:13+POOL_SIZE]`, the window that most tightly straddles the
true centre.

**Reminder about the addressable-vs-effective distinction.** The output raster
resolution is a rasterisation choice (see the deployment notes) and can be
10 m regardless of `POOL_SIZE`. `POOL_SIZE` controls the *effective footprint*
— how large a neighbourhood contributes to each prediction. Clay's patch is
the floor: no `POOL_SIZE` value gets you a genuine 10 × 10 m footprint.

**Usage.**

```bash
# One Clay pass — writes clay_cache/identity.npz (~940 MB for 4.6k chips,
# CLS + centre 7×7 patch tokens per chip).
python precompute_clay_embeddings.py

# Sweep pool sizes without re-running Clay.
for POOL in 1 2 3 5; do
  for SEED in 42 123 456; do
    KELP_POOL_SIZE=$POOL HEAD_SEED=$SEED python train_head.py
  done
done
# → results/head_seed{SEED}_p{POOL}/
```

Cache size: `N × (1 + K²) × 1024 × 4 bytes`. For N=4,609 and K=7 that's
~940 MB, versus ~46 MB for a single pool-specific cache. The trade is worth
it as soon as you touch more than one pool — a Clay pass is ~10 min on GPU,
head training is a few minutes per seed.

**Migration.** The old pipeline wrote a pool-specific cache
(`identity_p{POOL}.npz`, 2048-D per chip). The new pipeline writes a single
`identity.npz` (CLS + centre 7×7 patches) and `train_head.py` refuses old
caches with a clear error. Re-run `precompute_clay_embeddings.py` once after
this refactor; the pool-specific files can then be deleted (kept around for
now — they don't cost much and let old trained heads be reproduced from their
matching cache).

## Splits (algorithm)

The 2026-07-17 pipeline replaces the older component-graph + macro-region logic.
Two independent stages produce the split JSON per seed:

### Stage A — 75/15/15 split of A-carrying location-clusters

1. **Cluster ALL chips by location.** Any two chips (P or A) whose lat/lon
   fall within `CLUSTER_RADIUS_KM = 0.05` (50 m — exact-location safety)
   go into the same cluster via union-find over a haversine BallTree. 50 m
   is effectively "same lat/lon allowing GPS noise" — it catches multi-scene
   `_sN` siblings (all at the same coord) and the small number of P/A pairs
   sharing an observation coordinate at different dates or for different
   species. Chips further than 50 m apart are treated as independent, so
   pairs sitting 100 m – 1 km apart can end up in different splits (and teach
   the model that nearby locations can legitimately carry different labels).
2. **Partition clusters into A-carrying vs P-only.** A-carrying clusters
   contain at least one ABSENT chip and may also contain co-located P chips
   (22 mixed clusters in the current pool). P-only clusters contain PRESENT
   chips only.
3. **Determine each A-carrying cluster's primary (cloud_bin, water_bin)** from
   the mode of its A chips' `(cloud_region / 0.05, wf_region / 0.10)` bin
   values.
4. **Assign whole A-carrying clusters to train/val/test.** Within each
   (cloud, water) bin, iterate clusters in a seed-shuffled order and place
   each in whichever split is *most under* its per-bin target
   (0.75 / 0.15 / 0.15 of the bin total, measured in A chip count).

Cluster granularity limits how close the achievable ratio is to 75/15/15.
Overall achieved split ratios are **74–78 / 12–13 / 10–13%**.

**Guarantees**:
- All 1,533 A chips are placed; no A chip is dropped.
- Exact-location safety on ALL chips (P as well as A): any two chips within
  50 m end up in the same split.

### Stage B — hierarchical PRESENT subselection (~1.9:1 P:A)

Two sources of P per split:

1. **FORCED-P** — P chips inside A-carrying clusters go to the same split
   as those clusters (exact-location safety). The 14 mixed P/A clusters in
   the current pool contribute this way.
2. **FREE-P** — P-only clusters participate in the greedy nearest-neighbour
   assignment inside each A chip's water bin:
   - Per water bin, iterate the split's A chips in seeded random order.
   - Matching distance is `LAMBDA_W · |wf_A − wf_cluster| + |b02_A − b02_cluster|`
     with `LAMBDA_W = 2000` — b02 is the primary key, but water shifts within
     the coarse `WATER_W = 0.10` bin still contribute to the tie-break.
   - **Per-bin chip-count cap**: keep picking clusters until `chips_in_bin`
     reaches `P_A_RATIO_TARGET · A_in_bin_in_split`, then stop. This avoids
     high-water bins over-contributing because their P-only clusters carry
     2–5 chips each (cluster-count cap would have added 3–5× more chips
     per pick in dense bins, dragging the aggregate water median up).
   - Whole clusters are picked atomically — a free cluster with 2 co-located
     P chips (rare) goes as a unit, keeping P-P exact-location safety intact.

This preserves water-fraction alignment as tightly as the bin+distance
matching allows, approximates the b02 range within each water bin, and
enforces exact-location safety P-side. The chip-count cap trades ~10 %
fewer P chips in the splits (union: 4,609 vs 5,064 without the cap) for
much tighter cloud + water distributions between P and A.
### L2 sanity (linear classifier on QC only)

Trained on the split's train, evaluated on its test. Numbers below are
from the pre-2026-07-27 pipeline (cloud-first P fetch, no chip-count cap,
no `LAMBDA_W`); pending re-run on the current splits:

### Split JSON format

Per seed the pipeline writes two files:

```json
splits/a_split_seed42.json  →  { "seed": 42, "train_a_ids": [...], "val_a_ids": [...], "test_a_ids": [...] }
splits/split_seed42.json    →  { "seed": 42, "train_chip_ids": [...], "val_chip_ids": [...], "test_chip_ids": [...] }
```

The first is the A-only stratified split (Stage A output); the second is the
final chip split with P subselected (Stage B applied). `train_head.py` reads
the second.

### Determinism note

Iteration order over Python dicts (`clusters.items()`, `by_bin.items()`,
`a_by_wbin.items()`) depends on insertion order, which in turn depends on
row order in the source CSV. If the CSV is regenerated with a different row
order, running `make_splits.py` on the same seeds produces splits with
identical **statistical properties** (matching-distribution guarantees,
ratios) but slightly different **exact chip IDs**. The models on disk are
tied to the split files currently in `splits/`.

### Pipeline changes since the 0.89 ROC baseline

The 3-seed mean jumped from 0.893 to 0.974 test ROC (+0.081) after four
data-quality fixes:

1. **Mislabel removal**: 145 chips where the same ABSENT observation had
   been fetched twice (once mislabeled `class_tag=present`) were dropped.
2. **PRESENT-only candidate CSV**: `build_high_precision_candidates.py`
   was fixed to stop mixing ABSENT rows into the PRESENT fetch input.
3. **Symmetric cloud policy**: `QC_STRICT_PRESENT` now uses `sort="date"`
   (first-acceptable by date proximity) instead of "cleanest-first". P
   was previously cherry-picked to the very cleanest scene while A kept
   multiple scenes — this leaked "cleanest scene = PRESENT" as a QC
   shortcut. P cloud mean moved from ~0.011 → ~0.028 (A ~0.036, gap
   0.025 → 0.008).
4. **Chip-count cap + water term in matcher**: replaced cluster-count
   matching with chip-count matching per bin, and added `LAMBDA_W` water
   penalty. Fixed cluster-spillover in dense high-water bins and
   sharpened within-bin water alignment.

## Chip subsets (`KELP_CHIPS_SUBSET`)

The `KELP_CHIPS_SUBSET` env var routes every downstream artefact through a
subset-specific suffix so runs on different pools never collide. Two subsets
are currently in use:

| Value | Chips | Purpose |
|---|---:|---|
| `merged` (default) | ~4,600 P + ~1,500 A | Full pool across all kelp species — the "general" model. |
| `submerged` | ~2,200 P + ~1,500 A | Restricted to four deep-water species relevant to Sesimbra/Arrábida: *Saccorhiza polyschides*, *Laminaria hyperborea*, *Laminaria ochroleuca*, *Phyllariopsis brevipes*. ABSENT is species-agnostic (any chip with no PRESENT observation qualifies). |

Each subset carries its own:
- `$KELP_DATA_DIR/s2_chips_{subset}/{chips.h5,chips_metadata.csv}` — chips + metadata
- `$KELP_DATA_DIR/clay_cache/identity_{subset}.npz` — Clay embedding cache
- `$KELP_DATA_DIR/clay_cache/raw_center_{subset}.npz` — raw S2 pixel cache (pixel head only)
- `training/splits_{subset}/` — split JSONs
- `training/results_{subset}/` — trained heads + eval outputs

The `merged` subset uses un-suffixed paths for backward compatibility with
pre-subset runs. Assembly of the `submerged` subset from the merged pool is
in [`chip_generation/assemble_submerged.py`](../chip_generation/assemble_submerged.py).

## Deployment split (`split_single.json`)

The 3-seed splits (§ Splits above) leave 10–13 % of chips in a test set for
honest evaluation. For the **deployment** head — the one used in
`rasterise.py` and `rasterise_pixel.py` to produce actual Sesimbra maps — we
want maximum training data, so `make_single_split.py` produces a single
train/val split with no test set:

- Same 50 m location safety and (cloud_bin, water_bin) balancing as
  `make_splits.py`, but only two partitions instead of three.
- `--n-candidates 50` runs the greedy P subselection 50 times with different
  seeds and keeps the split with the lowest KL divergence between P and A on
  the (cloud, water) marginals — a tighter match than any single-seed draw.
- Writes `splits_{subset}/split_single.json`.
- `train_single.py` (chip head) and `train_single_pixel.py` (pixel head) read
  this file and skip the test-set stage.

The 3-seed splits are used for model comparison (pool sweep, pixel vs pool
sweep) because they give per-metric std across seeds. The single split is
used only to train the final deployment head.

## Pixel head

**Design.** Every chip is centred on its observation coord (PRESENT: reported
GPS ≤ 10 m unc; ABSENT: snap-to-water). The labelled pixel is therefore
always the chip-centre S2 pixel (64, 64) — which sits inside Clay patch
(14, 14) on the 28×28 patch grid. At training time this is functionally
equivalent to pool=1 with 6 extra spectral features; the win is at
*inference*.

**Training input (2054-D per chip):**
- CLS token (1024) — chip-global context
- Clay patch (14, 14) (1024) — the centre patch, cached at local (4, 4) in
  the stored 7×7 window
- Raw S2 (6) — Clay-normalised reflectance at pixel (64, 64), cached
  separately by [`precompute_raw_center.py`](precompute_raw_center.py)

**Inference (rasterise_pixel.py).** Bilinearly upsample the 28×28 Clay
patch grid to 128×128, concatenate with per-pixel raw S2, run the head at
every one of the 16,384 pixels per chip. Sesimbra bbox = 40 chip anchors →
~655k head calls; runs in a few seconds on GPU.

## Rasterisation (dense P(kelp) maps)

Given a bbox and an S2 L2A scene ID, both `rasterise.py` and
`rasterise_pixel.py` produce a Float32 GeoTIFF of P(kelp) at 10 m resolution
in the scene's UTM CRS. They share the same tiling / masking pipeline; they
differ only in how the head is applied.

**Pipeline (both scripts).**

1. **STAC lookup** — fetch the scene item from Earth-Search
   (element84 STAC), then read the 6 Clay bands (blue/green/red/rededge1/
   nir/swir16) + SCL over the bbox from the L2A COGs, aligned to the scene's
   native 10 m UTM grid via `from_bounds`.
2. **Tile with overlap** — cover the bbox with 128×128 chip anchors on a
   `stride_px` (default 64 = half-chip overlap) grid. Half-chip overlap
   means every interior pixel is covered by 4 chips → smoother mosaic
   boundaries.
3. **Batch Clay** — for each batch of `batch` anchors, resize 128→224,
   normalise per Clay's per-band mean/std, run Clay v1.5 encoder → CLS +
   28×28 patch grid.
4. **Apply head** (differs — see below).
5. **Mosaic with overlap averaging** — sum probabilities into `prob_sum`
   and increment `prob_cnt` per pixel; final `prob = prob_sum / prob_cnt`.
6. **SCL land / cloud / cirrus mask** — post-hoc set land (SCL 4/5/7/11),
   cloud (SCL 3/8/9/10), and nodata (SCL 0) pixels to NaN. This does not
   influence Clay or the head, only the final raster.

**Head application — `rasterise.py` (chip head):**
Run the head at every one of the 28×28 patch positions per chip →
28×28 probability grid, then bilinearly upsample to 128×128 before
splatting into the mosaic. Native resolution is ~46 m (one Clay patch);
the 10 m raster is a smooth upsample of that. 784 head calls per chip.

**Head application — `rasterise_pixel.py` (pixel head):**
Bilinearly upsample the 28×28 Clay patch grid to 128×128 (per-pixel Clay
context), concatenate with per-pixel raw S2 (already Clay-normalised),
broadcast CLS, then run the 2054-D head at every one of the 16,384 pixels
per chip. Native resolution is 10 m — each pixel gets its own decision
from its own spectra + interpolated neighbourhood. 20× more head calls
per chip than the chip version; head runs per-chip inside a batched
Clay pass to bound VRAM.

### Depth masking (optional)

Kelp beds in Arrábida sit above ~30 m depth; deeper pixels in the raster
are false positives from open-water spectra. `apply_bathymetry_mask.py`
fetches EMODnet bathymetry via WCS (public, no auth, ~115 m native),
reprojects onto the raster grid, and NaN-masks pixels where depth exceeds
`--max-depth-m` (default 30 m). Over the Arrábida bbox this removes 55.9 %
of pixels — mostly the deep water south of the shelf break.

**Cache round-trip.** `--bathy-out` writes the fetched bathymetry to disk
in the raw EMODnet convention (negative = below sea level). `--bathy-cache`
loads that file back on subsequent runs instead of refetching. Both paths
apply the sign flip on read, so round-trips are lossless.

## Sesimbra CCMar evaluation

### Pixel-aggregated CCMar evaluation

CCMar has 60 quadrat events (53 PRESENT + 7 ABSENT) from the Aquaserv 2026
survey. Their GPS points fall inside just 34 unique S2 pixels — the test is
tiny and dominated by geometry — but it's the only real-world ground truth
we have for the Sesimbra site. OR-based pixel aggregation: a pixel is
PRESENT if *any* event landing in it is PRESENT.

From `training/results_submerged/sesimbra_model_comparison_with_pixel.csv`
(n=34 pixels: 32 P / 2 A; best-threshold F1):

| Model | ROC-AUC | F1_PRESENT | F1_ABSENT |
|---|---:|---:|---:|
| `merged_p1` | 0.828 | 0.897 | 0.400 |
| `submerged_p1` | 0.812 | 0.877 | 0.364 |
| `submerged_p5` | **0.984** | **0.984** | **0.800** |
| `submerged_pixel` | 0.719 | 0.815 | 0.286 |

**Interpretation.** `submerged_p5` dominates, but with only 2 negative
pixels the F1_ABSENT column is 3 events wide — a single flip changes the
number by 0.15. The pixel head loses because per-pixel decisions concentrate
probability into 10 m spots that don't necessarily land on the same pixel as
the CCMar quadrat centre; pool=5's ~229 m footprint smooths over that
misalignment. This experiment does not prove per-pixel supervision is
useless — it proves that chip-level supervision does not transfer to
sub-46 m spatial precision on the CCMar geometry, which is what we expected.
